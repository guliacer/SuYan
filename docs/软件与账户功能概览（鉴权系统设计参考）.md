# 素言 SuYan · 软件与账户功能概览（供鉴权系统设计参考）

> **受众**：接手本项目的其它 AI（用于设计 / 实现 / 加固「鉴权系统」）。
> **目的**：让接手方在不逐文件通读源码的情况下，准确理解「软件是什么」+「账户系统现状」+「鉴权相关技术约束」，并据此开展设计。
> **口径**：本文所有技术细节均来自当前仓库代码（`docs/账号登录实施总方案.md`、`account-api/`、`electron/main/account/`、`src/features/account/`），非规划臆测。
> **关键提示**：现有 `account-api/` 是**本地参考实现 / 联调后端**，不是生产服务。详见本文「十、当前实现状态与诚实清单」。

> **当前实现口径（2026-08-30）**：Electron 客户端已经收敛为 Guli Identity 的 OIDC 公共 PKCE 客户端。Google、GitHub、Linux.do 等第三方登录由 Guli Identity 页面统一完成；客户端不再保存或实现这些平台的 OAuth provider，也不需要 `client_secret`。本文中保留的旧 Account API / 多 provider 契约仅用于迁移参考，历史 provider 的 `account.json` 会在启动读取时直接删除。

## 一、软件定位：素言 SuYan 是什么

素言是一款**本地优先（local-first）的桌面素材管理工具**，跨网络通知推送是其扩展能力（PC ↔ 手机，见 TapRelay）。

- **形态**：Electron 桌面应用（非 SaaS、非 Web 服务）。
- **核心业务**：管理「图片素材（图库）」与「提示词 / 账号 / API 配置 / 工作流（灵感库）」两类本地数据。
- **本地优先**：所有用户素材存于本机 `data/library/`（库为 `data\library\`），登录 ≠ 云同步。账号只负责「身份确认 + 导出作者信息」，第一阶段不引入云端素材同步。
- **已有 AI / 自动化能力**（鉴权设计时需考虑其边界）：
  - 远程 AI 调用（WorkBuddy / 豆包 Doubao），走代理设置；
  - 本地图片分类模型 **EfficientNet-Lite4-11-int8**（ONNX + onnxruntime-node）；
  - 本地 NSFW 分级模型；
  - **TapRelay** 手机推送（PC 端默认 `localhost:1122`，外网经 cloudflared 隧道 `wss://win.guliacer.dpdns.org`）；
  - **ComfyUI 本地收件服务** `127.0.0.1:9477`（仅本地回环，无鉴权头，供 ComfyUI `POST /guli/suyan/import` 推送图片）。

> 给鉴权设计的启发：除账号系统外，其余本地服务（TapRelay、ComfyUI 收件）目前均无鉴权。若「鉴权系统」覆盖范围超出账号登录，需把本地回环端口也纳入威胁模型。

## 二、技术栈与不可绕过的架构约束

- **技术栈**：Electron 43 + React 19 + TypeScript + Vite + Tailwind 4 + Zustand 5 + pnpm 11。
- **IPC 四层模式（强约束）**：所有桌面能力必须经
  ```
  electron/shared/ipcChannels.ts   →  IPC 通道名定义
  electron/main/ipc/registerIpcHandlers.ts  →  主进程 handler 注册
  electron/preload/index.ts        →  contextBridge 白名单
  src/types/suyanApi.ts            →  渲染层类型
  ```
- **渲染层（Renderer）禁止**：直接 `import electron`、`import node:fs`、直接使用 `ipcRenderer`、直接保存 token、直接发起 OAuth 网络请求、直接处理 refresh token。
- **所有 IPC 返回 `IpcResult<T>`**，复用现有 `handleResult` / `AppError` 体系；不得重新引入通用 `ipcRenderer.invoke/send/on`，不得用「万能 IPC channel」。
- **数据落盘**：敏感字段用 `safeStorage` 加密；JSON 用原子写。本地库主存储必须是 `library.json + images/`（另有 `prompts.json`、`account.json`、`view-settings.json`、`ai-settings.json`）。

## 三、账户系统总览：边界划分

```
                SuYan Electron（OIDC 公共 PKCE 客户端）
                          │  HTTPS + Discovery
                          ▼
                  Guli Identity（统一身份服务）
              ┌────────────┼─────────────┐
              ▼            ▼             ▼
          授权页面      Token / JWKS     UserInfo
```

- **Electron 客户端**负责：UI、Discovery、PKCE/state/nonce 生成、本地 token 安全存储、登录态恢复、导出注入作者信息。
- **Guli Identity** 负责：邮箱注册/登录以及 Google、GitHub、Linux.do 等第三方登录、授权码交换、用户资料和令牌。
- **核心原则**：身份服务负责认证，Electron 主进程负责安全，Renderer 负责 UI，导出系统只消费统一 `AuthorInfo`。

## 四、数据模型（统一 User + 多 Identity）

> 当前客户端只接收 Guli Identity 的统一身份。`uid` 使用 `issuer + sub` 稳定派生；不要把邮箱单独当作唯一身份。

```text
User
├── uid            (SuYan 自有 ID，UUID)
├── username
├── avatarUrl?
├── email?
├── emailVerified  (0/1)
├── createdAt / updatedAt
└── identities[]   (多身份绑定)
      ├── provider        "guli"
      ├── issuer          Guli Identity issuer
      ├── providerUserId
      └── linkedAt?

AccountSession   = { user, accessToken, refreshToken, expiresAt }
AuthorInfo       = { uid, username, avatarUrl? }   ← 导出系统统一消费
```

渲染层可见最小结构（`AccountPublicStatus`）：`{ status, user, provider }`，其中 `status ∈ "initializing" | "authenticated" | "unauthenticated"`。**渲染层绝不接触 accessToken / refreshToken / PKCE / HTTP。**

## 五、鉴权机制详解（设计鉴权系统的核心依据）

### 5.1 密码

- 算法：**scrypt**（随机盐 16B，`N=16384, r=8, p=1, keylen=32`），哈希串格式 `scrypt$N$r$p$saltB64$hashB64`。
- 校验：`timingSafeEqual` 防时序攻击；`password_hash` 为 `null`（OAuth 用户）时直接判失败。
- 策略：`EMAIL_RE` 校验 + 长度 6–128；密码**只走 HTTPS，绝不写入日志 / localStorage / Zustand persist / account.json**。

### 5.2 Access Token = HS256 JWT（对称签名，重点！）

- 结构：`header{alg:"HS256",typ:"JWT"}` + `payload{sub:uid, iat, exp}` + `HMAC-SHA256(secret)`。
- `expiresAt` 为**毫秒时间戳**；TTL 默认 **15 分钟**（受 `ACCESS_TOKEN_TTL_MS` 控制）。
- **⚠️ 关键决策点**：当前用 **HS256 对称密钥**（`JWT_SECRET`，来自后端环境变量）。任何需要**独立验证**该 token 的一方（其它服务 / 其它 AI）必须能拿到同一个 `JWT_SECRET`，否则应改为 **RS256 非对称**（公钥验签、私钥签名）。生产部署必须显式配置 `JWT_SECRET`，参考实现的「随机生成」仅适合开发。

### 5.3 Refresh Token（轮换制，防重放）

- 生成：`randomBytes(32)` → base64url；DB **只存 SHA-256 哈希**，绝不存明文。
- TTL 默认 **30 天**（`REFRESH_TOKEN_TTL_MS`）。
- **轮换**：每次 `/auth/refresh` 签发新 token 的同时，立即将旧 token 哈希置 `revoked=1`（单次使用）。
- `/auth/logout`：吊销该用户**全部** refresh token（含历史仍存活者）。

### 5.4 OAuth（Guli Identity Authorization Code + PKCE + state + nonce）

- 流程：客户端通过 Discovery 获取端点 → 生成 `code_verifier`、`code_challenge=S256(verifier)`、随机 `state`/`nonce` → 服务端内存登记挂起会话（TTL 10 分钟）→ 应用内授权窗口打开授权页 → Guli Identity 完成登录或第三方登录 → 回跳 `suyan://oauth/callback` → 主进程单次消费 state → 使用原始 verifier 调用 token endpoint → OIDC 库校验 ID Token 签名、issuer、audience、nonce 和过期时间 → 读取 UserInfo（仅补充资料）→ 落盘。
- Guli Identity 是 public PKCE 客户端，token 请求不发送 `client_secret`；Discovery、authorization、token、userinfo 和 JWKS 端点必须使用 HTTPS。
- 自定义协议：`suyan://oauth/callback`，**绝不**宽泛放行所有 `suyan://`。
- 防：state 不匹配 / 回调重放 / authorization code 重放 / open redirect / 未知 provider / 未知协议。
- 当前 OAuth 入口只有 `guli`；邮箱、Google、GitHub、Linux.do 等登录由 Guli Identity 统一处理。微信开放平台网站应用需要企业/个体户资质，不提供个人账号配置。

### 5.5 本地 Token 存储（Electron 主进程）

- 落盘结构 `data/library/account.json`（`schemaVersion:1`）：`user` / `provider` / `tokenEncrypted` / `updatedAt`。
- `tokenEncrypted` = `AccountTokenPayload{accessToken, refreshToken, expiresAt}` 经 **`safeStorage`** 加密后的 base64；`safeStorage` 不可用时退化为 `dev1:` + base64（明文仅内存，不落盘、不打印）。
- `account.json` 损坏 / 缺失 → 记录脱敏错误、隔离损坏文件、恢复为未登录，**绝不让素材库打不开**。

### 5.6 Token 刷新（全局锁）

- `TokenManager.refreshIfNeeded()`：未过期直接返回；已过期时通过 `refreshInFlight` 单飞 Promise，多并发请求共享同一次刷新，避免重复 refresh；refreshToken 失效时**清除登录态，不无限重试**。

## 六、Account API 端点契约（与 Electron 客户端对齐）

错误统一：`{ code: "ACCOUNT_*", message }`，成功返回 `{ session }` 或 `{ user }`。

| 方法   | 路径                                | 说明                                                                        |
| ---- | --------------------------------- | ------------------------------------------------------------------------- |
| POST | `/auth/register`                  | `{email,password}` → `{session}` 或 `{verificationRequired, devVerifyUrl}` |
| POST | `/auth/login`                     | `{email,password}` → `{session}`；未验证 403 `EMAIL_NOT_VERIFIED`             |
| POST | `/auth/refresh`                   | `{refreshToken}` → `{session}`（**轮换**，旧 token 立即失效）                       |
| POST | `/auth/logout`                    | `Bearer` + `{refreshToken?}` → 吊销该用户全部 refresh token                      |
| GET  | `/auth/me`                        | `Bearer` → `{user}`                                                       |
| POST | `/auth/verify-email`              | `{token}` → `{user}`（`EMAIL_VERIFY_MODE=token` 时用）                        |
| GET  | `/auth/verify-email?token=`       | 浏览器验证落页                                                                   |
| POST | `/auth/oauth/exchange`            | `{provider,code,verifier,redirectUri,state}` → `{session}`（PKCE S256 校验）  |
| POST | `/auth/link`                      | `Bearer` + 同 exchange 参数 → 绑定当前用户；已属他人 409 `LINK_CONFIRM_REQUIRED`        |
| POST | `/auth/unlink`                    | `Bearer` + `{provider}` → 解绑                                              |
| GET  | `/oauth/mock/:provider/authorize` | **仅联调**：模拟授权页（`MOCK_OAUTH=1`）                                             |
| POST | `/oauth/mock/:provider/confirm`   | 确认授权 → 302 回跳 `suyan://oauth/callback?state&code`                         |
| POST | `/oauth/mock/:provider/deny`      | 拒绝 → 302 回跳 `?state&error=access_denied`                                  |
| GET  | `/health`                         | `{ok:true,service:"suyan-account-api"}`                                   |

> 具体 URL 可按实际后端调整，但**职责必须保持**（见方案 §四）。

## 七、数据库 Schema（`account-api`，`node:sqlite`，零外部依赖）

```
users(uid PK, email UNIQUE, password_hash, username NOT NULL,
      avatar_url, email_verified INTEGER DEFAULT 0, created_at, updated_at)

identities(provider, provider_user_id, user_uid FK→users(uid) ON DELETE CASCADE,
           linked_at)  PK(provider, provider_user_id)
          INDEX idx_identities_user(user_uid)

refresh_tokens(token_hash PK, user_uid FK, expires_at INTEGER,
               created_at, revoked INTEGER DEFAULT 0)

email_verifications(token PK, user_uid FK, expires_at INTEGER, used INTEGER DEFAULT 0)

oauth_codes(code_hash PK, provider, provider_user_id, code_challenge,
            redirect_uri, expires_at INTEGER, used INTEGER DEFAULT 0)
```

- JWT secret / OAuth secret / client_secret **不入库**；refresh/验证/授权码均只存哈希。
- `email` 可为 `null`（纯 OAuth 用户）。

## 十、当前实现状态与诚实清单

**已落地（代码已实现）**：

- Electron 端 Guli Identity OIDC 公共 PKCE 客户端：Discovery、S256、state/nonce 单次校验、ID Token 验证、userinfo 补充、refresh token 轮换与 `suyan://` 回调。
- 统一 User+Identity 模型，身份键使用 `issuer + sub`；未验证邮箱拒绝登录；Renderer 不接触 token。
- Token 安全存储（safeStorage）、全局刷新锁、导出统一注入 AuthorInfo、全套错误码、IPC 四层、单元测试与 Windows 打包验证（Phase 0–8 已完成）。

**参考实现边界（生产化前必须补齐，禁止冒充正式功能）**：

- `account-api/` 是**本地联调后端**：Mock OAuth 授权页、随机 JWT 密钥、`EMAIL_VERIFY_MODE=auto` 默认跳过邮件验证、无 SMTP。
- `account-api/` 仍是旧的本地邮箱 / Mock OAuth 参考实现，不是当前 Electron 登录依赖，也不应作为生产身份服务；旧 provider 的 `account.json` 不再兼容，启动时会删除。
- 真实登录依赖 Guli Identity 的生产 client_id、回调登记和 HTTPS Discovery；未配置时客户端抛 `ACCOUNT_PROVIDER_UNAVAILABLE`，**绝不伪造本地登录**。

## 十一、给接手 AI 的设计指引（鉴权系统）

### 11.1 必须遵守的硬约束

1. 渲染层禁止持有 token / 处理 OAuth；一切经 IPC 与主进程。
2. Token 不明文落盘、不进日志（含 DEBUG）；password 永不落盘。
3. 统一 User + 多 Identity；**不**仅凭相同邮箱自动合并账号（防账号接管）。
4. OAuth 必须用 PKCE(S256) + state + 单次消费；回调必须精确匹配 `suyan://oauth/callback`。
5. refresh token 轮换 + 全局刷新锁 + 失效即清登录态。
6. Guli Identity 必须使用 Discovery + Authorization Code + PKCE(S256)，校验 issuer/audience/nonce/email_verified，且生产端点全部 HTTPS。
7. 错误按 `code` 分支，不按 `message` 猜测。
8. 账号数据不破坏已有 `library.json/prompts.json`；`account.json` 损坏不影响素材库。

### 11.2 在动手前需向用户确认的开放问题

- **Q1 定位**：要做的「鉴权系统」是（a）**加固 / 生产化素言自有账号鉴权**（替换参考实现、接真实 OAuth、加 SMTP/审计/限流），还是（b）**给外部 AI / 插件 / 服务访问素言**做鉴权（即素言作为资源方，对外签发/校验凭证）？二者架构不同。
- **Q2 密钥体系**：若外部方需独立验证素言用户 token，是否将 HS256 升级为 **RS256（非对称）**？否则需共享 `JWT_SECRET`（有泄露面）。
- **Q3 范围**：鉴权是否覆盖非账号的本地服务（TapRelay `1122`、ComfyUI 收件 `9477`）？当前二者无鉴权。
- **Q4 部署形态**：生产 Account API 部署在哪里（独立服务 / 现有 Ubuntu `guliacer.dpdns.org`）？是否有密钥管理（Vault / 环境变量 / KMS）？

### 11.3 建议的实施顺序（若做生产化加固）

1. 先定 API Contract + 密钥体系（HS256→RS256 决策）→ 2. 接真实 OAuth 凭证 → 3. 邮件验证（SMTP）→ 4. refresh 轮换审计 + 速率限制 → 5. 账号接管防护的交互式确认流 → 6. 密钥轮换与配置外置 → 7. 测试 + 打包验证。
