# 素言 SuYan 账号登录系统最终落地实施方案

> 本文档是账号登录系统的**正式实施标准**（2026-08-21 由用户确认，替代“临时豁免”语境）。接手实现的智能体必须按本文档检查现有代码、补齐设计缺口并落地，禁止自由发挥。
>
> 核心目标：**不是把登录页面做出来，而是把「账号体系 → 登录 → OAuth → Token → 本地安全存储 → 登录态恢复 → 账号切换 → 导出作者信息 → 打包验证」完整闭环**。
>
> 项目已明确要求四种渠道，并要求导出物携带用户名和头像。未具备个人开放平台资质的社交 OAuth 渠道不提供配置。

> **当前实现已更新（2026-08-30）**：上述“项目自建邮箱 / Google / Linux.do / GitHub provider”是历史方案。当前 Electron 只接入 Guli Identity OIDC：使用 Discovery、Authorization Code + PKCE(S256)、state + nonce 和 public client（不发送 `client_secret`）；邮箱及第三方登录均在 Guli Identity 页面完成。下文旧 Account API/provider 章节仅保留作迁移参考，不得据此在客户端恢复独立 provider；检测到旧 provider 的 `account.json` 时直接删除。

### 当前实现标准

- issuer：`https://auth.guliacer.dpdns.org`（生产必须 HTTPS）。
- Discovery：`/.well-known/openid-configuration`，授权、令牌、userinfo、JWKS 端点均从 Discovery 读取并强制 HTTPS。
- 客户端：配置 `GULI_IDENTITY_CLIENT_ID` 的公共 PKCE 客户端，不配置 `client_secret`。
- 授权页：使用系统默认浏览器打开真实的 Guli Identity / 第三方登录页面，复用浏览器已有会话、密码管理器和通行密钥；回调：桌面协议 `suyan://oauth/callback`，state/nonce/code_verifier 只在主进程内存保存，TTL 不超过 10 分钟，回调成功或失败都单次消费 state。
- 身份：以 `issuer + sub` 作为稳定身份键；`email_verified` 非 `true` 时拒绝登录；不按邮箱自动合并账户。
- Token：只在 Electron 主进程流转，使用 safeStorage 加密落盘；默认 scope 为 `openid email`，只有确需离线访问时才增加 `offline_access`。

> **实施进度（2026-08-30）**：Electron 端 Guli Identity OIDC（Discovery、PKCE、state/nonce、ID Token 校验、refresh 轮换和安全存储）已完成，类型检查、全量 Vitest（171 个文件 / 1218 项）和 Windows 快速打包已通过。真实登录仍取决于 Guli Identity client_id、回调登记以及服务端把 Discovery 端点统一修正为 HTTPS。

## 一、总目标

以本方案作为账号系统的正式实施标准，对当前 SuYan Electron 项目进行完整检查、设计补全、代码实现、测试和 Windows 打包验证。

目标不是只实现一个登录 UI，而是完成一套可以长期维护、可扩展、安全、真正可用的账号系统。

## 三、账号系统必须采用「统一 User + 多 Identity」模型

不要把 Google、Linux.do、邮箱做成三套独立账号。

统一模型：

```text
User
├── uid
├── username
├── avatarUrl
├── email
├── createdAt
├── updatedAt
└── identities
      ├── email
      ├── google
      ├── linuxdo
      └── github
```

`uid` 是 SuYan 自己的用户 ID。第三方 provider 的用户 ID 只属于 Identity：

```text
Identity
├── provider
├── providerUserId
└── userId
```

同一个用户以后可以绑定邮箱 / Google / Linux.do / GitHub，而不会产生四个不同的 SuYan 用户。

## 四、必须明确「账号后端」与 Electron 客户端的边界

Electron 不是账号服务器，必须存在统一的 SuYan Account API：

```text
                SuYan Electron
                      │
                    HTTPS
                      │
                      ▼
              SuYan Account API
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
      User          OAuth         Token
      System       Providers      System
```

后端至少负责：

```text
POST /auth/register
POST /auth/login
POST /auth/refresh
POST /auth/logout
GET  /auth/me

GET  /oauth/google/start
GET  /oauth/google/callback

GET  /oauth/linuxdo/start
GET  /oauth/linuxdo/callback

POST /auth/link
POST /auth/unlink
```

具体 URL 可以根据实际后端情况调整，但职责必须保持。

如果当前项目尚无账号后端：**不要伪造一个本地登录系统冒充正式账号功能**。应首先建立 Account API Contract，并将 API 地址、OAuth Client ID、Redirect URI 等配置做成环境配置。不得把 `client_secret`、JWT secret、OAuth secret 写入 Electron 客户端。

> **参考实现（2026-08-21）**：`account-api/` 已落地为本地可运行的 SuYan Account API 参考后端（零运行时依赖：`node:http` + `node:sqlite` + `node:crypto`），实现上表全部端点（register/login/refresh/logout/me + oauth exchange + link/unlink），含 SQLite 持久化、邮件验证占位与 **Mock OAuth 授权页**（走完整 PKCE + state + 回调流程，供客户端在无任何开放平台凭证时端到端联调）。运行方式与联调指引见 `account-api/README.md`；冒烟测试 `node node_modules/vitest/vitest.mjs run account-api/test/api.smoke.test.ts`。

## 六、统一 Provider 接口

当前唯一 OAuth 客户端是 Guli Identity，旧 provider 接口只作为历史设计记录，不得重新实现：

```ts
interface OAuthProvider {
  readonly id: "guli";
  startLogin(): Promise<void>;
  handleCallback(callback: OAuthCallback): Promise<AccountSession>;
}
```

统一返回：

```ts
interface AccountSession {
  user: AccountUser;
  accessToken: string;
  refreshToken: string;
  expiresAt: number;
}
```

Provider 的差异只存在于 Account 层内部。React 不允许出现 `if provider === google` 这类 OAuth 逻辑。

## 七、OAuth 必须使用 PKCE + state

桌面 Electron OAuth 必须优先：Authorization Code + PKCE + state。

流程：

```text
点击「Google / Linux.do / GitHub / 邮箱登录」
    ↓
生成 code_verifier
    ↓
生成 code_challenge
    ↓
生成随机 state
    ↓
保存临时 OAuth session
    ↓
    打开系统默认浏览器授权页
    ↓
Guli Identity 登录或第三方授权
    ↓
suyan://oauth/callback
    ↓
校验 state
    ↓
提交 code + verifier
    ↓
获取 token
    ↓
获取 User
```

必须防止：state 不匹配、callback 重放、authorization code 重放、open redirect、恶意 callback、未知 provider、未知协议。

## 八、OAuth 回调建议使用自定义协议

优先 `suyan://oauth/callback`。不要让 Renderer 自己监听 OAuth，Electron 主进程负责：register protocol → receive callback → validate → resolve pending OAuth。

现有 `electron/main/index.ts` 已有自定义协议体系，需要在不破坏原协议的情况下增加 OAuth callback。

特别注意：`externalUrlPolicy.normalizeExternalUrl` 目前只允许 http/https。OAuth 自定义协议必须单独处理，不能简单把 `suyan://` 加入一个宽泛的“所有外部协议都允许”的规则。

## 九、账号本地数据设计

新增 `data/library/account.json`：

```json
{
  "schemaVersion": 1,
  "user": {
    "uid": "...",
    "username": "...",
    "avatarUrl": "...",
    "email": "..."
  },
  "provider": "guli",
  "updatedAt": "..."

```

Token 不允许直接写进 JSON，必须用 `safeStorage` 保存 accessToken / refreshToken（可整体加密一个 payload：`{ accessToken, refreshToken, expiresAt }`）。必须复用项目现有 safeStorage 与 JSON 原子写机制（见 `.codex/rules/08` R1.1）。

## 十、token 生命周期必须完整实现

不能只有 `login → save token`，必须：

```text
登录 → accessToken/refreshToken → 正常 API 请求 → accessToken 即将过期 → refresh → 更新 token
```

refreshToken 失效时：清除本地 token → 清除登录态 → UI 回到未登录。不要无限 refresh。

必须防止多个请求同时触发 refresh：应有全局 refresh lock（`refreshPromise`），多个请求等待同一个 refresh。

## 十一、应用启动时恢复登录态

```text
Electron Main → AccountService.initialize() → 读取 account.json → 读取 safeStorage token → 检查 token → 必要时 refresh → GET /auth/me → 恢复 User
```

React 启动时处于 `initializing`，不能直接显示“未登录”，否则会出现“启动 → 瞬间显示登录 → 又变成用户名”。正确状态：`initializing | authenticated | unauthenticated`。

## 十四、邮箱注册必须是真正的账号流程

至少：邮箱、密码、确认密码。注册：输入邮箱 → 后端创建账号 → 发送验证邮件 → 验证 → 登录。

如果后端暂时没有邮件验证能力，必须明确标记为后端缺失项，**不要在客户端伪造邮箱验证**。密码只传 HTTPS，不得写入日志、localStorage、Zustand persist、account.json。

## 十五、账号绑定规则必须设计

Guli Identity 内部可能关联多个登录方式，但客户端只接收 Guli Identity 的统一身份。必须定义：

- 情况 A：Guli Identity 返回已验证的 `issuer + sub` → 直接恢复对应用户。
- 情况 B：Guli Identity 内部完成第三方登录 → 客户端只消费统一 OIDC 身份，不感知平台 provider。
- 情况 C：邮箱与现有本地记录相同 → **不能仅凭邮箱自动合并**，必须由身份服务完成明确、安全的绑定流程，否则存在账号接管风险。

## 十六、导出系统统一使用 AuthorInfo

不要每个导出模块自己去读取账号。统一：

```ts
interface AuthorInfo {
  uid: string;
  username: string;
  avatarUrl?: string;
}
```

主进程 `AccountService.getCurrentUser()` 统一提供，然后 Archive Export / Image Export / Prompt Export 按需使用。

## 十九、图片导出

默认策略：**不要默认修改用户原图**。单图导出首先保持原图内容不变，作者信息优先通过 metadata 或伴随信息保存。如果产品明确要求图片上出现头像 + 用户名，再实现水印。水印逻辑必须独立（`imageAuthorWatermark.ts`），不要把复杂图片处理直接塞进 `exportImageToLocal()`。

## 二十、头像策略

账号头像来源 `AccountUser.avatarUrl`，**不能**使用 `utils/authorAvatarSources.ts`（那是提示词站点作者头像）。第三方头像 URL 失效时显示默认头像，不能让整个账号系统进入错误状态。

## 二十二、错误体系

账号系统必须有明确错误码：

```text
ACCOUNT_NOT_LOGGED_IN
ACCOUNT_INVALID_CREDENTIALS
ACCOUNT_EMAIL_NOT_VERIFIED
ACCOUNT_TOKEN_EXPIRED
ACCOUNT_REFRESH_FAILED
ACCOUNT_NETWORK_ERROR
ACCOUNT_OAUTH_CANCELLED
```

UI 必须根据 `error.code` 处理，不得用 `message.includes("xxx")` 判断。

## 二十三、网络与代理

项目已有 `proxySettingsStore.ts` / `remoteAiClient.ts`。账号网络请求也必须考虑项目代理设置，不要自己重新实现一套代理逻辑。Account API Client 应提供 `request()`，统一处理 proxy、timeout、HTTP error、JSON error、network error。

## 二十四、日志安全

账号相关日志允许：OAuth started / completed、Login succeeded / failed、Refresh succeeded / failed。禁止输出：password、accessToken、refreshToken、authorization code、client secret、PKCE verifier，即使 DEBUG 日志也不能输出。

## 二十五、必须考虑应用退出

退出应用时**不需要**主动删除 refreshToken（否则用户每次打开都必须重新登录）。只有用户主动退出登录才清除 accessToken / refreshToken / account session。refresh token rotation 后拿到新 token 必须原子更新。

## 二十六、账号切换

支持用户 A 退出、用户 B 登录。切换后当前用户、头像、用户名、导出作者必须全部立即更新。

第一版**不要**擅自把 library / prompts / images 变成“每个账号一份”。账号系统第一阶段只负责：Identity、Authentication、User profile、Export author，除非产品另行要求云同步。

## 二十七、不要把本地素材库与账号强绑定

当前 SuYan 是本地素材管理工具，**登录 ≠ 云同步**。登录只是确认用户身份 + 导出作者信息。第一阶段不要顺便加入云端素材 / 云同步 / 云端图片 / 云端提示词，避免项目范围失控。

## 二十八、旧数据兼容

新增 `account.json` 不能影响已有 `library.json` / `prompts.json` / `view-settings.json` / `ai-settings.json`。没有 `account.json` 时默认 `unauthenticated`，绝对不能启动失败。`account.json` 损坏时：记录脱敏错误、备份/隔离损坏文件、恢复为未登录，不能导致整个素材库打不开。

## 二十九、测试必须覆盖这些场景

- Account Store：启动未登录、启动已登录、logout、login、refresh、refresh failure。
- Account Crypto：encrypt、decrypt、invalid payload、safeStorage unavailable。
- OAuth：state valid、state invalid、callback malformed、unknown provider、duplicate callback、cancelled。
- Serialization：account.json 旧 schema、新 schema、损坏 JSON。
- Export：未登录导出、已登录导出、author 正确写入、旧 ZIP 可以导入、旧 JSON 可以导入。
- IPC：success、AppError、network error、not logged in。

## 三十一、实施顺序

不要一次性修改全部文件，严格按以下阶段实施：

- **Phase 0：代码审计** — 先读取 `AGENTS.md`、`.codex/rules/*`、IPC 四层文件、`libraryPaths.ts`、`aiSettingsStore.ts`、`promptAccountCrypto.ts`、`proxySettingsStore.ts`、`index.ts`、`archiveStore.ts`、`imageFiles.ts`、`promptStore.ts`，并检查 `git status` / `git branch --show-current`。禁止覆盖其他智能体未提交修改。
- **Phase 1：先定义 Account Contract** — User / Identity / AccountSession / AccountProvider / AccountError / AuthorInfo，以及 Account API、IPC API。这一阶段不要先写 UI。
- **Phase 2：本地 AccountService** — accountStore / accountCrypto / tokenManager / accountService，先实现登录态保存、读取、退出、恢复。
- **Phase 3：邮箱** — 完整打通 register / login / refresh / logout / restore。
- **Phase 4：Guli Identity OIDC** — Discovery、PKCE、state、nonce、callback、protocol、OAuth session。
- **Phase 5：真实环境验证** — 配置生产 client_id、回调登记和 HTTPS Discovery，不在 Electron 内新增第三方 provider。
- **Phase 6：UI** — LoginDialog / RegisterDialog / AccountMenu / UserAvatar。
- **Phase 7：Export** — 统一注入 AuthorInfo，修改 archiveStore.ts / promptStore.ts / imageFiles.ts。
- **Phase 8：完整测试与打包** — 执行：

```bash
node node_modules/typescript/bin/tsc -p tsconfig.json --noEmit
node node_modules/typescript/bin/tsc -p tsconfig.electron.json --noEmit
node node_modules/vitest/vitest.mjs run
pnpm package:win
```

并报告：TypeScript Renderer / TypeScript Electron / Vitest / Windows Package 各自通过/失败。

## 三十二、绝对禁止的实现方式

禁止：

1. 在 Renderer 保存 refresh token。
2. 把 token 放 localStorage。
3. 把 token 放 Zustand persist。
4. 把 password 写入 account.json。
5. 在日志输出 token。
6. 在日志输出 password。
7. Renderer 直接请求 OAuth。
8. Renderer 直接访问 `ipcRenderer`。
9. 使用一个万能 IPC channel。
10. 在 Electron 内为 Google、GitHub、Linux.do 等平台复制独立登录状态。
11. 自动根据相同邮箱合并账号。
12. 为了实现登录擅自引入数据库。
13. 为了实现登录擅自增加云同步。
14. 修改已有本地素材库的数据模型。
15. 破坏旧 ZIP/JSON 导入兼容性。
16. 用 mock/fake OAuth 冒充正式登录功能。
17. 将 OAuth client secret 打包进 Electron。
18. 用宽泛协议白名单放行 `suyan://`。
19. 为了“快速完成”跳过 refresh token。
20. 只测试首次登录而不测试应用重启。

## 三十三、如果当前后端能力不足

如果发现当前项目没有 Guli Identity client_id、回调登记或 HTTPS Discovery，不要停止整个改造。应完成：

```text
Electron Account Architecture
+ API Contract
+ Guli Identity OIDC client
+ Mockable Provider
+ 完整 IPC
+ 完整 UI
+ 本地 session 管理
+ Export author
+ 测试
```

并明确输出 `BLOCKED_EXTERNAL_DEPENDENCIES`，列出缺失的：Guli Identity client_id、回调登记、HTTPS Discovery 或 email_verified 声明。但是不能把“外部配置未提供”包装成“真实登录已验证”。
