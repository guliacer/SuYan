# 版本隔离策略

## 当前约定

| 版本 | 含义 | 代码位置 | 发布物 |
|------|------|----------|--------|
| **0.1.0** | 第一个正式版（已冻结） | 标签 `v0.1.0`、分支 `release/0.1.0` | GitHub Release `v0.1.0` |
| **0.2.10** | 第二个正式版（已锁定） | 标签 `v0.2.10`、`master` 历史提交点 | GitHub Release `v0.2.10` |
| **0.3.6** | 当前正式版（已锁定） | 标签 `v0.3.6`、`master` 发布提交 | GitHub Release `v0.3.6` |
| **0.3.7+** | 后续开发版本 | `master` 的 `package.json` | 新标签 / 新 GitHub Release |

## 铁律

1. **首版不可被覆盖**  
   - 禁止改写标签 `v0.1.0`、分支 `release/0.1.0` 的历史（勿 force-push）。  
   - 禁止删除或替换 GitHub Release `v0.1.0` 上的安装包 / 便携包。  
   - 本地归档建议：`release/archive/v0.1.0/`（若存在）只读保留。

2. **后续版本按版本号迭代**
   - 在 `master` 上继续开发。  
   - `v0.3.6` 已发布并冻结；后续功能或修复必须先升级到更高版本，例如 `0.3.7`。
   - 本地 `package:win` 使用当前 `package.json` 版本更新 `release/win-unpacked` 快速便携目录，不生成安装包或 ZIP，也不要求每次本地迭代都创建 Git 标签或 GitHub Release。
   - 准备正式交付时执行 `pnpm package:win:release`，并按实际版本建立新的标签和 GitHub Release。

3. **产物文件名必须带版本**  
   - 安装包 / 便携 ZIP 依赖 electron-builder 的 `${version}`，例如 `素言-Setup-0.2.0.exe`。  
   - 不得用新包覆盖旧版同名文件（若历史上存在无版本后缀的文件，后续一律改用带版本名）。

4. **热修复旧版（可选）**  
   - 仅修 0.1.x：在 `release/0.1.0` 上改 → 版本改为 `0.1.1` → 标签 `v0.1.1` → 新 Release。  
   - 不要把 0.2 的功能 cherry-pick 进 0.1 维护线，除非明确是兼容性补丁。

5. **检查更新**  
   - 应用通过 GitHub `releases/latest` 与 semver 比较；新版本必须发正式 Release（非 draft），用户端才会提示更新。

6. **升级可直接覆盖，但 `data\` 需用户自行备份**
   - 安装版与便携版都支持直接覆盖升级，不要求用户先卸载。
   - 素材库、设置、词库都在软件目录下的 `data\`。**安装版覆盖升级和卸载都会删除它**（NSIS 卸载器对 `$INSTDIR` 执行 `RMDir /r`，升级时整个目录被移进临时目录后丢弃）；便携版换目录解压则不会自动带过去。
   - 这是既定取舍：不实现 NSIS `customRemoveFiles` 保留 `data\`，也不把数据迁出软件目录。详见 `.codex/rules/08` R3.2。
   - 补偿措施：检测到新版本时，关于对话框显示备份提醒和「打开数据目录」按钮，引导用户把整个 `data\` 复制到软件目录之外，升级后再复制回来。
   - **发布说明必须包含这段备份提醒。** 不要建议用"导出分享包 / 导入分享"做升级备份——ZIP 是分享格式，会重签条目 `id`、将 external 转为 managed；虽携带所选作品对应的分类与标签库并保留原始时间，仍不含完整词库、个人设置、API 密钥或外部库挂载。

7. **已锁定版本默认冻结**
   - 已打标签并发布的版本（当前 `v0.1.0`、`v0.2.10`、`v0.3.6`）默认不再改动。
   - 后续任何修改都面向更高版本，先升级 `package.json`，再开发、打包和发布，不回改已锁定版本的代码、标签或 Release 产物。

## 日常流程（新版本）

```text
1. master 开发 / 修 bug
2. 在未推送阶段按需升级 `package.json` 版本（如 `0.3.0` → `0.3.1`）
3. pnpm package:win（开发快速包，仅更新 release/win-unpacked）
4. 准备推送 GitHub / 创建 Release 时执行 pnpm package:win:release（生成安装包和便携 ZIP）
5. 用户确认推送时，git tag 对应版本并推送到 origin
6. gh release create 对应版本并上传全量产物
7. 在 Release 说明里写明「升级前请备份软件目录下的 data 文件夹」
```

## 分支关系

```text
release/0.1.0  ── 冻结首版（= v0.1.0）
       │
       └─（历史点）── master ── 0.2.x → v0.2.10（已锁定）→ v0.3.6（已锁定）→ 0.3.7+
```
