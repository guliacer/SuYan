# 版本隔离策略

## 当前约定

| 版本 | 含义 | 代码位置 | 发布物 |
|------|------|----------|--------|
| **0.1.0** | 第一个正式版（已冻结） | 标签 `v0.1.0`、分支 `release/0.1.0` | GitHub Release `v0.1.0` |
| **0.2.10** | 第二个正式版（已锁定） | 标签 `v0.2.10`、`master` 提交点 | GitHub Release `v0.2.10` |
| **0.3.0** | 当前开发线（占位图修复 + 网页助手 MVP） | `master` 的 `package.json` | 新标签 / 新 Release（待发） |
| **0.3.1+ / 0.4.0** | 后续开发 | 默认分支 `master` 的 `package.json` | 新标签 / 新 Release |

## 铁律

1. **首版不可被覆盖**  
   - 禁止改写标签 `v0.1.0`、分支 `release/0.1.0` 的历史（勿 force-push）。  
   - 禁止删除或替换 GitHub Release `v0.1.0` 上的安装包 / 便携包。  
   - 本地归档建议：`release/archive/v0.1.0/`（若存在）只读保留。

2. **后续改动只进新版本**  
   - 在 `master` 上继续开发。  
   - `package.json` 的 `version` 必须 **高于** 已发布版本（当前开发线为 `0.2.0`）。  
   - 每次正式对外交付：升版本号 → 打新标签（如 `v0.2.0`）→ 新建 GitHub Release → 上传 **带新版本号文件名** 的产物。

3. **产物文件名必须带版本**  
   - 安装包 / 便携 ZIP 依赖 electron-builder 的 `${version}`，例如 `素言-Setup-0.2.0.exe`。  
   - 不得用新包覆盖旧版同名文件（若历史上存在无版本后缀的文件，后续一律改用带版本名）。

4. **热修复旧版（可选）**  
   - 仅修 0.1.x：在 `release/0.1.0` 上改 → 版本改为 `0.1.1` → 标签 `v0.1.1` → 新 Release。  
   - 不要把 0.2 的功能 cherry-pick 进 0.1 维护线，除非明确是兼容性补丁。

5. **检查更新**  
   - 应用通过 GitHub `releases/latest` 与 semver 比较；新版本必须发正式 Release（非 draft），用户端才会提示更新。

6. **升级可直接覆盖，但 `data\` 需用户自行备份**
   - 安装版与便携版都支持直接覆盖升级，不要求用户先卸载。
   - 素材库、设置、词库都在软件目录下的 `data\`。**安装版覆盖升级和卸载都会删除它**（NSIS 卸载器对 `$INSTDIR` 执行 `RMDir /r`，升级时整个目录被移进临时目录后丢弃）；便携版换目录解压则不会自动带过去。
   - 这是既定取舍：不实现 NSIS `customRemoveFiles` 保留 `data\`，也不把数据迁出软件目录。详见 `.codex/rules/08` R3.2。
   - 补偿措施：检测到新版本时，关于对话框显示备份提醒和「打开数据目录」按钮，引导用户把整个 `data\` 复制到软件目录之外，升级后再复制回来。
   - **发布说明必须包含这段备份提醒。** 不要建议用"导出分享包 / 导入分享"做升级备份——ZIP 是分享格式，会重签条目 `id`、重置时间戳、丢弃分类树，且不含任何设置与词库。

7. **已锁定版本默认冻结**
   - 已打标签并发布的版本（当前 `v0.1.0`、`v0.2.10`）默认不再改动。
   - 后续任何改动如无特别说明，都视为面向**新版本**：先 bump `package.json` version（`0.2.10` → `0.2.11` / `0.3.0`）再开发，不回改已锁定版本的代码、标签或 Release 产物。
   - 仅当明确要求改动某个已锁定版本时才动它（如热修复走 `release/x.y.z` 维护线，见铁律 4）。

## 日常流程（新版本）

```text
1. master 开发 / 修 bug
2. 确认 package.json version 已 bump（如 0.2.11）
3. pnpm package:win
4. 生成便携 ZIP（文件名含版本）
5. git tag v0.2.11 && git push origin v0.2.11
6. gh release create v0.2.11 --latest 并上传新产物
7. 在 Release 说明里写明「升级前请备份软件目录下的 data 文件夹」
```

## 分支关系

```text
release/0.1.0  ── 冻结首版（= v0.1.0）
       │
       └─（历史点）── master ── 0.2.x 开发线 → v0.2.10（已锁定）→ 未来 v0.2.11 / v0.3.0 …
```
