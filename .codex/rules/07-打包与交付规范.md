# 打包与交付规范

## 适用范围
适用于所有代码修改后的打包验证、产物更新和交付说明流程。

## 规则条目

### R1: 每次修改后必须执行开发快速包验证
**断言**：每次修改项目代码后，必须在完成就近验证后自动执行 `pnpm package:win`。该命令只构建并更新 `release\win-unpacked\` 目录，不生成 NSIS 安装包或 Portable ZIP；交付说明中必须明确报告快速打包是否成功以及 `release\win-unpacked\素言.exe` 与 `resources\app.asar` 的更新时间。若打包失败，必须说明失败原因和下一步处理方式，不得只停留在 `pnpm build`。

准备推送 GitHub 或创建正式 Release 时，才执行 `pnpm package:win:release`，该命令在同一构建链路上额外生成 NSIS 安装包与 Portable ZIP。

### R2: 文件被占用时自动关闭应用再打包，完成后自动重启
**断言**：执行打包或同步 release 目录时，若遇到 `EBUSY`、文件被占用、资源锁定等错误，必须自动检测并关闭正在运行的应用进程（`素言.exe` 或从 `release\`、`release-next\`、`release-*\` 目录启动的 Electron / `suyan-core.exe` 进程），然后重新执行打包流程，不得因文件被占用而交付失败或停留在中间状态。**凡是为打包而被关闭的应用进程，必须在打包成功后自动重新启动（`release\win-unpacked\素言.exe`），恢复用户被中断的使用状态；不得关闭后就停在那里不管。** 若进程确实无法关闭（权限不足、句柄拒绝释放等），必须如实报告原因与下一步，不得静默失败。

**处理流程**：
1. 检测到文件占用错误
2. 查找并确认占用进程（进程名包含"提示词"/`素言`/`suyan-core`，或路径匹配 `release*\win-unpacked`）
3. 强制关闭相关进程
4. 等待 2 秒确保文件句柄释放
5. 重新执行打包/同步
6. 验证产物更新时间
7. **若第 3 步曾关闭过应用，打包成功后自动重新启动 `release\win-unpacked\素言.exe`，让用户回到打包前的使用状态**

**违规特征**：出现 `EBUSY` 报错后直接停止、要求用户手动关闭应用、把产物放到 `release-v2` 等临时目录而不同步回正式 `release` 目录、或为打包关闭了应用却在完成后不再自动拉起。

### R3: 打包产物必须同步到正式 release 目录
**断言**：最终交付的打包产物必须位于 `release\win-unpacked\` 目录中。若因文件占用等原因临时输出到其他目录（如 `release-next\`、`release-v*\`），必须在文件解锁后将 `app.asar` 和 exe 等关键产物同步回 `release\win-unpacked\`，并在交付说明中确认正式目录已更新。

### R4: 正式包必须启用基础代码保护
**断言**：执行 `pnpm package:win` 时必须对打包暂存目录中的 `dist-electron` 做 JS 混淆，关闭 production source map，启用 Electron asar integrity fuses（`enableEmbeddedAsarIntegrityValidation`、`onlyLoadAppFromAsar`），正式包禁用 DevTools；打包时生成 `app-integrity.json` 供运行时完整性校验；剪切板/AI/批量等敏感模块使用更强混淆；开发用 `dist-electron` 不得被混淆脚本直接覆盖。
**示例**：
```text
pnpm package:win
# package-win.cjs 复制 dist-electron 到 stage 后调用 scripts/obfuscate-electron.cjs
# electronFuses.enableEmbeddedAsarIntegrityValidation = true
```
**违规特征**：把未混淆明文主进程 JS 打进 release、开启 sourcemap、或正式包默认开放 DevTools。

### R5: 版本隔离，禁止覆盖已发布版本
**断言**：已发布版本（`v0.1.0`、`v0.2.10` 及用户后续明确推送并发布的版本）为冻结交付物；当前 `master` 的 `0.3.x` 在用户推送到 GitHub 前属于未发布迭代线，允许按补丁版本连续升级（如 `0.3.0` → `0.3.1` → `0.3.2`），不提前建立标签或 Release 锁定点。用户推送后，才以实际推送/发布版本建立锁定点。所有正式产物文件名必须包含当前 `package.json` 版本；不得 force-push 已锁定标签、不得替换已发布 Release 附件。策略全文见 `docs/VERSIONING.md`。
**违规特征**：覆盖 `v0.1.0` 或 `v0.2.10` 的已发布附件；在 `0.3.x` 尚未推送前擅自创建冻结标签；把新功能合进已锁定分支且不建立新版本；删除已发布 Release 资产。

### R6: 正式包数据与日志必须在软件目录内
**断言**：安装版与便携版的用户数据（`library.json`、图片、设置）必须写入软件根目录下的 `data\`，日志写入 `logs\`；不得默认使用 `%APPDATA%\SuYan`。`electron .` 与本地 `release\win-unpacked` 共用 `release\win-unpacked\data`。正式包升级时若本地 `data\` 尚无库，才把旧 AppData 库迁入。细则见 `08-数据库与状态管理规范` R3 与 `09-日志管理规范` R1。
**违规特征**：正式包继续把素材库写到 C 盘 AppData；便携版数据落在系统临时目录；本地开发或 `package:win` 迭代切到 `%APPDATA%\SuYan`。

### R7: 发布包必须包含精简语言包、便携 ZIP 与 sidecar，且不含 FFmpeg 二进制
**断言**：`package-win.cjs` 必须：
1. `electronLanguages: ["zh-CN", "en-US", "ja"]`，不得打全量 Electron 语言包；
2. `pnpm package:win` 的 `win.target` 只能是 `dir`，用于开发快速更新 `win-unpacked`；`pnpm package:win:release` 必须显式设置发布模式，使 `win.target` 产出 `nsis` 安装包与 `zip` 便携包（Portable 命名）；
3. 在 `package:win` 链路中构建并 stage Rust Core（`pnpm build:rust-core`），以 `extraResources` 的 `bin` 带出；媒体原字节复制使用 Node `fs.copyFile`，**不得**再打包 Go file helper；
4. vendor 仅 `jszip` + `sharp`（含 `@img/sharp-win32-x64` 原生文件），**禁止**将 `ffmpeg-static` 或任何 `ffmpeg.exe` 打进 `resources/vendor`；FFmpeg 由按需组件系统在用户首次使用时安装。
**违规特征**：开发快速包仍生成安装包或 ZIP；正式包体积因全量 locale 或内置 FFmpeg 膨胀；发布模式缺少 Portable ZIP；缺少 `bin` 中的 rust-core；vendor 出现 `ffmpeg-static`；`resources/bin` 出现 `go-file-helper`。

### R8: 构建产物目录必须先清空，删掉的模块不得随 `app.asar` 出货
**断言**：
1. `tsc` 只写不删——删除或重命名 `electron/**/*.ts` 后，它编出的 `.js` 会永久留在 `dist-electron/`，而 `package-win.cjs` 会把整个 `dist-electron` 拷进 stage 并打进 `app.asar`。因此 `build:electron` 必须在编译前清空 `dist-electron`（`node scripts/clean-dist.cjs dist-electron && tsc -p tsconfig.electron.json`），与 `build:renderer` 清 `dist` 对称。
2. `clean-dist.cjs` 接受目标参数，但必须用白名单限死（当前 `dist`、`dist-electron`），未知目标与路径穿越一律抛错，不得扩展成"删任意传入目录"。
3. 删除模块后的验收**不能**只看 `pnpm package:win` 成功或 `resources/bin` 内容，必须验证 `app.asar` 内部：`npx asar list release/win-unpacked/resources/app.asar | grep -i <名字>` 加 `grep -a "<字符串>" release/win-unpacked/resources/app.asar`。
**示例**：
```text
# 删掉 electron/main/runtime/goFileHelper.ts 之后的真实事故
dist-electron\electron\main\runtime\goFileHelper.js   ← 源码已删，产物残留
→ 被 copyDirectory("dist-electron") 带进 stage → 打进 app.asar 出货
```
**违规特征**：`build:electron` 是裸 `tsc`；`dist-electron/electron/**/*.js` 存在没有对应 `.ts` 的孤儿文件；以"打包成功"作为模块删除干净的证据。回归测试见 `tests/unit/packageWin.test.ts`（clean 步骤断言 + 孤儿产物扫描）。

### R9: 打包流程必须保护开发状态数据，删除前必须显式确认
**断言**：打包流程（`package-win.cjs` 及所有 `pnpm package:*` 脚本）不得静默删除或覆盖 `release/win-unpacked/data` 和 `release/win-unpacked/logs` 目录下的任何用户数据。具体保护措施：

1. **nestedPreserve 保护**：`promoteStagedRelease` 必须将 `win-unpacked` → `{ data, logs }` 加入 `nestedPreserve`，确保同步 stage 到 release 时绝不删除现有用户数据目录。
2. **交互确认**：若 `release/win-unpacked/data` 存在，打包流程在 `promoteStagedRelease` 前必须通过交互式终端提示用户确认（`[Y/n]`），用户输入非 `y`/`yes`/空 时立即中止并退出码 1。可通过 `SUYAN_PACKAGE_CONFIRMED=1` 环境变量跳过交互（用于 CI/自动化）。
3. **forbiddenPackagePayloadNames**：打包 stage 和最终产物中不得包含 `library.json`、`ai-settings.json`、`view-settings.json`、`proxy-settings.json`、`window-state.json`、`acceleration-settings.json`、`.default-library-seeded`、`.startup-gallery-seeded`、`manifest.json` 等个人数据文件，`assertNoPersonalLibraryPayload` 必须在 stage 目录和最终产物中执行扫描。
4. **FFmpeg 完整性校验**：promote 前后必须检查已安装的 FFmpeg 组件是否丢失，若丢失则抛错中止。
5. **违规即中止**：任何试图删除 `data/` 或 `logs/` 的操作必须导致打包流程立即中止，并输出明确的中止原因。不得静默跳过、不得回退到降级产物。

**违规特征**：`package-win.cjs` 中 `promoteStagedRelease` 未传递 `nestedPreserve` 参数；`release/win-unpacked/data` 存在时打包流程直接运行不提示确认；打包后 `data/` 目录内容减少或丢失；`assertNoPersonalLibraryPayload` 被注释或移除；已安装的 FFmpeg 组件在 promote 后丢失。

**实现参考**：`package-win.cjs` 中的 `confirmDataDirectorySafety()`、`nestedPreserve`、`forbiddenPackagePayloadNames`、`assertNoPersonalLibraryPayload()`、`resolveInstalledFfmpegExe()` 和 `promoteStagedRelease()` 的 FFmpeg 校验。

**历史教训**：2026-08-23 曾因打包流程静默删除 `release/win-unpacked/data` 导致用户最新 75/76 条素材库丢失，仅从回收站恢复 52 条。此规则即为防止同类事故固化。
