## G01 — 启动、页面切换与渲染性能

### 归并范围
历史记录：P001、P002、P003、P004、P010、P028、P041、P059、P064、P065、P076。

这些记录共同指向同一类问题：启动或页面切换路径把大批派生计算、重组件挂载、图片解码或主题提交放在用户可感知的同步阶段，导致首屏白屏、点击无响应、返回首页卡顿或滚动掉帧。

### 共性根因
- 启动阶段执行全量提示词识别、词库同步、分类推断或其它派生计算；单条操作看似很快，累积后形成秒级阻塞。
- 词库工作区和大型页面在多个视图间反复卸载/重挂载，或收到每次渲染都变化的回调，导致 memo 无法生效。
- 同一份 prompt group、标签、图片数量或筛选结果在多个组件重复计算；未使用 Set、条件短路或稳定缓存。
- 缩略图 URL 按应用启动时间整体失效，图片淡入动画和布局提交在滚动期间扩大重绘范围。
- GPU 状态采集时机不正确，或直接用“关闭 GPU / 强制开启 GPU”的单一策略处理所有机器；主题切换和冷启动缺少可定位的首帧阶段日志。
- 单实例启动、首屏准备和加载更多流程没有统一的就绪状态，表现为白屏、重复启动或滚到底无反馈。

### 统一方案
1. 启动只读取必要的 library、视图设置和已保存缓存。启动页先展示真实内容；提示词识别、词库同步和批量后处理只处理首屏可见范围，剩余任务放到可取消、分批让出主线程的 idle 队列。
2. 词库页面按需首次挂载，挂载后在首页/画布之间保持挂载并用 hidden 隐藏；重组件使用 memo，持久化和移动操作使用稳定的 useCallback。只计算当前视图需要的数据。
3. 把昂贵派生结果提升到最高公共父组件并复用；去重使用 Set，非目标视图在 useMemo 内立即短路；不得在多个组件分别执行相同的全量分组、排序和计数。
4. 瀑布流使用顶边对齐的显式分列；缩略图 URL 使用素材文件名与 updatedAt 等稳定版本键，列表缩略图不做长时间淡入；为卡片增加布局/绘制隔离，保留分页和加载更多。
5. 默认使用可验证的 GPU 加速策略，GPU/渲染进程连续崩溃时自动降级并允许用户恢复；GPU 状态必须在 gpu-info-update 后采集，不凭过早日志追加激进 flags。
6. 为启动、首帧、视图切换、慢滚动、GPU 降级、单实例和批量后处理保留轻量结构化日志。日志应区分 render-start、layout-effect、first-raf、ready、IPC 和后台任务，不逐帧刷日志。
7. 首屏、主题切换、返回首页、滚到底和双击启动都必须以状态机或明确的 ready/loaded 状态驱动，禁止用短暂空内容或重复初始化掩盖真实状态。

### 统一回归边界
- 启动不得全量重建词库、扫描全部提示词、批量生成缩略图或阻塞渲染主线程。
- 首页与画布切换不得重复挂载已预热的词库工作区，隐藏工作区不得持续参与布局和绘制。
- 缩略图缓存缺失、过期、生成中、生成失败必须有可见回退路径；失败 URL 不写入会话缓存。
- 保持 P063 的滚到底加载更多、P064 的冷启动无白屏和 P065 的单实例行为。
- 启动页展示时长是预留窗口，不是可以为首屏指标牺牲的缓冲；就绪更快只能延长等待，不能缩短展示（见 `04-核心铁律与避坑.md` R12）。
- 所有性能优化先用日志和基准数据定位，再用 typecheck、测试和正式包复测；不得凭直觉叠加机制。

#### 追加：2026-09-02 — 启动页被自动收掉（预留时长退化为最小时长）
- 归属主题：G01
- 新增证据：正式包日志 25+11 次启动全部在 `elapsedMs` 约 912-975ms 就记录 `startup-overlay:exiting`，`startup-overlay:skip` 计数为 0（从未有人点跳过）；而启动页步骤动画最后一条要到 3.6s 才开始（`animationDelay: ${0.45 + index * 1.05}s`），画廊轮播间隔 2200ms。根因是常量语义退化：`STARTUP_OVERLAY_FIXED_MS = 6000`（预留墙钟窗口）被改成 `STARTUP_OVERLAY_MIN_MS = 900`（防闪白最小值），库就绪即刻放行。
- 统一方案变化：启动页时长回归「预留窗口」语义，见 `04-核心铁律与避坑.md` R12——放行开关只允许固定计时器与用户「跳过」两个写入点，数据就绪只能延长不能缩短；固定时长必须覆盖启动页自己的时间线。按用户设定定稿为总时长 9000ms、首图停留 2000ms、之后每 1500ms 翻一张，6 张图在 9 秒内全部翻到。画廊翻页改为按开播墙钟排期，不再用 `setInterval`，避免全屏阶段到淡出浮层的重挂载让首图停留重新计时。启动性能优化不得以缩短启动页展示时间来换首屏指标。
- 回归测试：`tests/unit/startupIntroHold.test.ts`、全量 Vitest 与两份类型检查。

## G02 — 媒体展示、缩略图与效果图组一致性

### 归并范围
历史记录：P011、P037、P052、P063、P075。

这些记录共同处理素材网格、瀑布流、效果图预览和缩略图缓存的展示一致性，核心目标是让布局稳定、图片可查看、滚动可继续、缓存可复用。

### 共性根因
- 使用 CSS column-count 导致瀑布流按列填充，少量结果被拉成整列或整行。
- 图片预览只设置最大尺寸，没有根据 naturalWidth/naturalHeight 主动计算适合视口的显示尺寸。
- 网格布局使用“非空列数量”替代用户选择的布局列数，精选或搜索只剩少量结果时列宽发生变化。
- 全局启动时间作为缩略图缓存键，或所有列表缩略图统一做长动画，导致跨启动重复解码和滚动重绘。
- 加载更多、缩略图回退和原始效果图排序没有被视为同一套媒体状态契约。

### 统一方案
1. 用 JavaScript 按每列当前高度做顶边分配；CSS 网格始终保留用户选择的列轨道，少量结果也保持稳定列宽。
2. 全屏预览加载图片真实宽高，按 min(96vw, 92vh × 宽高比) 计算目标尺寸，同时保留最大宽高约束，不裁切、不拉伸。
3. 缩略图 URL 使用素材自身内容版本，不用 Date.now 作为全库 cache busting；素材未变化时跨启动复用缓存，素材更新时通过 updatedAt 失效。
4. 缩略图加载必须覆盖缓存缺失、过期、生成中、生成失败四种状态；生成失败只回退到存在的原图，失败缩略图地址不得写入会话缓存。外部素材从解析出的原图生成缩略图。
5. 首页分页与 Grid 内 IntersectionObserver 分工明确，滚到底继续加载；慢滚动只在停止后汇总最大帧间隔和慢帧数量。
6. 同一提示词组的原始效果图固定为第一张，后续效果图按加入时间追加；收藏、缺失、最新导入都不得改变原图优先级。图片复制前必须按文件内容解码为 nativeImage，优先统一转换为 PNG，不依赖扩展名判断真实格式。

### 统一回归边界
- P011、P052 的少量结果和多列布局回归测试必须保留。
- P063 的加载更多不得因分页、缩略图回退或网格重排失效。
- P075 的缩略图失败回退、稳定缓存键、外部原图和原图排序回归必须保留。
- 覆盖扩展名与真实格式不一致的图片导入、复制和原始图第一/后续图追加顺序。

## G03 — Electron 边界、IPC、日志与编码

### 归并范围
历史记录：P005、P006、P007、P008、P009、P013、P015。

这些记录共同说明：桌面能力必须沿 Electron 三层边界流动，错误必须结构化并进入统一日志，项目中文文件必须始终按 UTF-8 读写。

### 共性根因
- 独立组件直接引用父组件局部变量，或 preload invoke 泛型与 SuyanApi 返回类型不一致。
- 日志桥函数散落在多个渲染组件；日志没有级别、模块和稳定路径；IPC catch 只返回错误而不写日志。
- AI/IPC 超时只有慢操作记录，没有错误码、通道、耗时和脱敏后的上下文。
- PowerShell、Node.js 或脚本读取项目中文文件时依赖默认编码，修改后造成乱码。

### 统一方案
1. React 只能调用 window.suyanApi；所有主进程能力由 preload + contextBridge 暴露最小白名单 API。组件依赖通过 props 或 hooks 传入，preload 泛型必须与共享类型完全一致。
2. IPC channel 集中声明，返回值统一为 { ok: true, data } 或 { ok: false, error }。渲染层不捕获并展示原始异常堆栈。
3. 统一使用 logger.info/warn/error/debug(module, event, details)。错误日志必须包含 code、message、IPC channel 和 durationMs 等必要字段；日志写入异步串行、不阻塞主流程，并通过 sanitizeDetails 脱敏。
4. 日志桥只保留一个共享实现。新代码不得继续扩散旧的 logStartupEvent；旧兼容层只有在迁移需要时保留。
5. 所有项目文件读取和写入显式使用 UTF-8；PowerShell 使用 Get-Content -Encoding UTF8，Node 使用 encoding utf8，Python 使用 encoding utf-8。

### 统一回归边界
- IPC 类型、错误返回、日志级别、敏感字段脱敏和 UTF-8 读取各有测试或静态检查。
- 错误不能只显示在 UI 而不落日志；日志不能包含 API Key、Token、完整提示词或图片二进制。2026-09-09 Grok 图生图 HTTP 415：`/images/edits` 按 xAI 契约发送 JSON（单图 `image`、多图 `images`），保留 Data URI 和 `b64_json` 返回，不发送 GPT 专用 size/output_format/background；415 日志记录 status/requestContentType，不误报图片损坏、不重发计费 POST。回归：`aiImageGeneration.test.ts`、`canvasRemoteIntegration.test.ts`。
- 渲染层不得出现 node:fs、node:path、electron 或 ipcRenderer 直接导入。

## G04 — 本地数据、外链索引与用户设置持久化

### 归并范围
历史记录：P014、P021、P058、P060、P061、P062、P073。

这些记录共同处理“重启、重新打包或外部文件变化后状态是否仍然正确”，统一原则是正式包本地数据可迁移、可恢复、可追溯，用户设置不能只存在内存。

### 共性根因
- library.json 直接覆盖写入，崩溃或断电时可能损坏。
- 正式包把 library、图片、设置和日志固定写入 AppData，便携版无法目录自包含；迁移后仍继续读旧路径。
- external 条目、托管副本和缺失源文件的展示/删除边界不一致。
- 侧边栏宽度、AI 快捷分析来源等用户可见设置只存在 React state；词库清空后被默认种子或旧 sibling draft 回种。

### 统一方案
1. library.json 采用临时文件写入后原子 rename；schema 变化提供迁移函数和回归测试。
2. 正式安装版和便携版数据写入软件目录 data，日志写入 logs；开发模式使用 AppData。首次正式启动从旧 AppData 自动迁移，成功后只读写新路径。打包不能覆盖 data 和 logs。
3. managed 素材复制到 data/library/images；external 只保存注册根目录下的相对索引。external 删除只能删除索引和应用缓存，不能删除用户原文件；源文件缺失时浏览和批量管理显示一致。
4. 用户可见设置必须有正式 JSON 字段，并经 preload、IPC、主进程 store 保存和恢复。侧边栏偏好、AI 分析来源、主题和视图偏好不得只存组件 state。
5. null 表示从未配置才允许种默认；用户明确清空得到的空数组或空域必须保持为空。每个词库工作区只写当前域，不能用挂载时的旧 draft 覆盖其它域或重新回种默认。
6. 迁移、清空、重启、重新打包和外链文件缺失都要同时验证内存状态、IPC 返回、磁盘 JSON、正式包 data 路径和 UI 展示。

### 统一回归边界
- 原子写入、迁移、external 删除保护、缺失条目、清空后重启、设置重新读取必须有测试。
- 正式包复测必须确认 release 目录下 data 和 logs 未被覆盖，并记录产物更新时间。
- 用户设置的保存失败要回滚或显示结构化错误，不能静默恢复默认。

## G05 — 构建、打包、正式包保护与运行一致性

### 归并范围
历史记录：P012、P018、P042、P043、P074。

这些记录共同处理“源码修了但正式包没修好”以及正式包可被轻易替换、解包或调试的问题。

### 共性根因
- 正式包文件被正在运行的进程占用，打包停留在临时目录或失败。
- 根目录 index.html 被 dist 构建产物覆盖，下一次 Vite 构建失去源码入口。
- 只改源码没有先 typecheck，打包继续沿用上一份成功产物；新增常量缺失时用户仍运行旧逻辑。
- 仅靠 asar fuse 和通用混淆不足以阻止换皮，且没有运行时完整性校验。

### 统一方案
1. package:win 前检查并关闭占用 release 文件的旧进程；构建完成后确认 release/win-unpacked/素言.exe、resources/app.asar 和安装包都已更新。
2. 根目录只保留源码入口 index.html，dist 和临时 stage 不得反向覆盖源码。
3. 代码改动按 typecheck → targeted test → pnpm test → pnpm package:win 顺序验证；AI/IPC 关键路径额外检查 app.asar 中实际函数结构和产物时间，区分配额错误与瞬时网络错误。
4. production 关闭 source map，对 dist-electron 混淆，启用 asar integrity fuse、onlyLoadAppFromAsar 和正式包关闭 DevTools；敏感模块使用更强混淆。
5. 打包后生成 app-integrity.json，对 package、主进程、preload、渲染 bundle 等做 SHA-256。正式包启动校验品牌字段和哈希，失败则记录并退出；开发模式跳过。清单必须在混淆后、打 asar 前生成。
6. 单实例启动、窗口健康、GPU 降级和正式包数据保护一起作为交付烟测，不把“打包命令成功”当作运行成功。

### 统一回归边界
- 版本号必须高于已发布版本，不覆盖旧 Release 附件。
- P074 类问题必须证明源码检查、typecheck、测试、app.asar 内容和最终 exe 时间一致。
- P042/P043 的安全保护不得影响开发模式调试，也不得覆盖 data、logs 和用户设置。

## G06 — 网络素材、视频导入与后台后处理

### 归并范围
历史记录：P022、P023、P024、P025、P026、P027、P038、P039、P040。

这些记录共同处理网络链接、视频文件和异步媒体处理，统一原则是先完成用户可感知的导入，再后台做昂贵后处理，同时保证媒体类型和下载任务不重复。

### 共性根因
- 网络素材导入默认弹窗询问保存方式，打断主流程；链接、托管副本和离线能力没有清晰边界。
- 视频导入同步读完整 Buffer、转码和生成缩略图，阻塞 IPC；前端词库同步继续占用“导入中”状态。
- 站点只在前端运行时生成签名或通过 API 返回真实视频，主进程复现旧签名或只读封面导致导入失败。
- 打开详情时重复触发同一下载，没有主进程和渲染层的 in-flight 去重。

### 统一方案
1. 第一版网络素材默认直接下载到本地，不弹保存方式确认框；用户明确选择链接模式时才建立 external 索引，并显示离线与源文件缺失状态。
2. 视频优先使用文件复制或流式处理，不把大文件无条件读入内存；文件落盘和最小 library 写入完成后立即返回，转码、缩略图和词库更新进入可取消后台队列。
3. 文件选择器绑定当前窗口并复用最近媒体目录；导入日志拆分选择、落盘、写库和后处理阶段，不能只记录一个 IPC 总耗时。
4. 对带签名的站点使用隐藏 BrowserWindow 让页面自己生成签名并拦截响应；WebToMind 等站点必须检查内容 API、videoUrl/videoUrls、video 标签和同路径视频兜底，真实视频优先于静态封面。
5. 主进程用 itemId 到 Promise 的 Map 做并发去重，渲染层用 Set 防止重复触发；无论成功、失败、超时都在 finally 释放在途状态。
6. 视频详情的操作栏按普通布局放在视频信息卡片之后，避免固定悬浮层遮挡导入区域；所有媒体导入返回结构化结果和明确失败状态。

### 统一回归边界
- 默认网络导入不再弹窗；链接模式不复制用户原文件，托管模式不保存外部绝对路径。
- 视频导入必须覆盖大文件、真实视频优先、转码失败回退、重复打开详情和并发下载。
- UI 显示导入完成后，后台处理仍可继续，但必须有独立状态和日志，不能让用户误以为导入未结束。

## G07 — 启动图库接入与视觉布局

### 归并范围
历史记录：P016、P017、P019、P020、P034、P035、P036、P048、P050、P051、P054、P055。

这些记录共同处理启动图库的“数据接入、资源安全、预览交互和视觉布局”，不能把 API/CSP/首显逻辑与纯 CSS 视觉问题拆成互相重复的记录。

- 主进程和 preload 已有图库能力但渲染层仍读编译期静态图片；自定义协议未同步加入 CSP。
- Electron ready-to-show 早于真实图库和首屏内容准备，或只截取固定三张图片。

### 统一方案
1. 启动图库统一使用 list/import/remove/resetStartupGallery API，共享 channel、返回类型和 UI 调用链；app-startup 协议同时核对 handler、CSP img-src、资源路径和打包文件。

5. 叠层卡片保持不透明，用内部蒙层表现远近明暗；z-index 只负责真实遮挡关系。文案面板使用按内容收缩的宽度，轻量蒙版只保证可读性，不抢占主视觉。

## G08 — 页面布局、浮层与响应式控件

### 归并范围
历史记录：P029、P031、P032、P044、P045、P046、P047、P049、P056。

这些记录共同处理 overflow、stacking context、固定定位和弹性布局引起的遮挡、裁剪、空白与换行，不应每次为同一定位原则新建问题。

### 共性根因
- tooltip、dropdown、menu 和回到顶部按钮挂在 overflow 或局部 stacking context 内，z-index 无法突破裁剪。
- 页面卡片和弹窗共用固定高度、内部滚动与 overflow-hidden，长内容被截断。
- 浮动按钮按窗口边缘定位而不是按内容容器定位，或复用通用 class 覆盖了 absolute/fixed。
- 固定宽度、max-h 和空格文案没有适配最长文本、宽屏内容和紧凑边栏状态。

### 统一方案
1. 所有 tooltip、popover、dropdown、menu 用 createPortal 挂到 body，以 fixed + getBoundingClientRect 定位，处理滚动、resize、Escape、外部点击和视口翻转。
2. 页面级内容使用自然主滚动，弹窗使用 bounded 内部滚动，通过 page/bounded 等显式布局模式区分，不能靠一套 height/overflow 规则兼容两种场景。
3. 回到顶部按钮脱离通用 tooltip 定位 class，按内容最大宽度和侧栏宽度计算，并放在内容卡片外侧；每个长列表页面都覆盖。
4. 长列表使用 min-h-0 flex-1 overflow-y-auto，数值气泡使用 whitespace-nowrap 和最小宽度；紧凑边栏进入图标模式后吸附到实际紧凑宽度，键盘调整可跨过断点。
5. 新增浮层或固定按钮后，检查最后一列、卡片底部、滚动条和窄屏边界，确保不会覆盖内容。2026-09-08 窗口缩放改用可见边框内的四边/四角热区，关闭外层 thickFrame 缩放；经白名单 IPC 由主进程读取鼠标位置、限制最小尺寸、失焦/松手停止。起点使用 pointerdown 坐标，松手补最后一帧，覆盖快速拖拽；阴影留边扩大到 36px 并加深，与启动壳同步。回归见 `windowResize.test.ts`、`windowChrome.test.ts`，实测左右边框拖拽。

### 统一回归边界
- Portal 浮层在 overflow-hidden、overflow-y-auto、侧栏与主内容交界处都要可见且位置跟随。

## G09 — 词库工作区、批量操作与首页入口

### 归并范围
历史记录：P030、P033、P053、P072。

这些记录共同处理“同一个入口在不同业务语义下复用旧组件”的问题，统一目标是让词库浏览、AI 设置和首页搜索入口只保留用户当前任务所需的信息。

### 共性根因
- 分类/标签内容已经从词库条目变成提示词组，但仍复用旧的条目选择集合，导致批量选择和删除数量不一致。
- 完整素材卡片直接复用到词库浏览，来源、预览、标签和操作过多，降低扫描效率。
- AI 设置把底层 action 拆成重复入口；首页搜索面板又把被明确移除的分类、类型、来源筛选重新渲染。

### 统一方案
1. 分类和标签工作区独立维护提示词组选择集合；全选、反选、取消、删除和卡片勾选都消费同一集合，删除时展开到素材 ID 并复用已有 store/API。
2. 共享卡片通过显式 compact/full variant 区分场景；词库浏览只保留标题、缩略图和必要选择框，完整浏览才展示来源、提示词预览和操作。
3. AI 规则设置按真实产品入口聚合分类识别和标签识别，来源、API、模型和规则作为右侧详情配置，不展示重复的底层 action。进入分类/标签入口时必须分别读取已保存的默认识别来源，不得固定选 actions[0]；当前入口内手动查看另一来源不改变默认值，点击默认星标则立即打开对应来源。服务商下拉每次打开定位已选项，重复选择当前服务商不能重置模型；切换服务商优先使用其符合当前能力的默认模型。回归覆盖 `aiSettingsEntrySelection.test.ts`、`aiSettingsModel.test.ts` 的 JSON 往返恢复与 `scripts/check-ai-settings-selection-ui.mjs` 的六入口切换、来源/模型/规则一致性、重新打开和保存失败回滚。
4. 首页顶部搜索面板只保留搜索框本体及其内部搜索按钮；筛选、统计、排序、导入和管理入口放到用户主动打开的弹窗、抽屉或独立页面。

### 统一回归边界
- 选择数量、卡片勾选、批量工具条和删除结果必须一致，且不绕过 IPC。
- compact 视图不能把完整卡片信息带回词库页面。
- 静态测试禁止首页搜索面板恢复素材目录、类型、来源和常驻筛选胶囊。

#### 追加：2026-09-03 — Guli Identity 多登录方式关联与资料闭环
- 归属主题：G09
- 新增证据：客户端已经能启动绑定事务并在确认后保持当前 UID，但生产 `GET /v1/account/link/google` 仍返回 404；仅有登录页或客户端按钮无法让邮箱、Google、Linux.do、GitHub 进入同一账户。

## G10 — AI 分类、标签、参数的语义隔离

### 归并范围
历史记录：P057、P066、P067、P068、P069、P070、P071。

这些记录共同处理 AI 输出、详情展示、词库同步和分类浏览之间的语义边界；同类问题必须持续补充同一套字段白名单、过滤规则和反例测试。

### 共性根因
- AI 分类把光线、色彩、景深、情绪和棚拍光等视觉属性误当稳定检索分类，或仅凭人物/幕布推断专业影棚、肖像摄影。
- 分类结果实际保存了多个 genreIds，但浏览、计数和筛选只消费 category/categoryId；重开后又因归并逻辑丢失附加分类。
- 参数分析把 category、suggestedTags 或分类胶囊写回标签，普通标签数量上限又错误截断附加分类。
- 标签分析从 category 字段兜底取词，并按颜色前缀或模糊包含关系分组，导致实体落入风格或“其他标签”；不同语义被压入“趣味配方”。2026-09-10 复核：固定短词表漏掉白桦树、矮几、闭目等常用实体；后续全库 42 组又发现蝴蝶发夹按蝴蝶、玻璃杯按玻璃、手持相机按相机等局部词误分。旧整理写入 groupLocked 后，原预览不再给出纠正建议，不能把“已确认”当作语义正确的证据。

### 统一方案
1. 分类只允许稳定检索维度：内容类型、人物题材、服饰造型、场景类型/细分、主题领域、风格流派、应用场景、文化语境和时代风格。光线、色彩体系、技术手法、景深、情绪氛围属于视觉属性，不进入分类持久化或展示。
2. 对专业影棚、肖像摄影等边界使用可观察证据判断；模型提示词和 taxonomy 入口都过滤禁止维度，详情展示旧数据时也再次过滤。
3. 分类浏览、计数和筛选统一消费 categoryId + genreIds 的完整集合，并用 Set 防重复；多分类保存、重开、菜单计数和提示词组命中必须走同一 taxonomy 工具。
4. 参数、分类、标签是单向隔离域。参数分析不修改 category；标签上限只限制普通可见标签，不截断已保存附加分类；标签通道只消费 tags，不使用远程 category 兜底。
5. 标签优先按实体语义分组：环境、动物、道具与配饰、动作姿态、构图景别、材质纹理、光影和风格分别处理；颜色加实体按实体归类，不能仅按颜色前缀判断风格；禁止模糊包含替换不同标签。`tagKnowledge.ts` 统一层级分组、安全同义词和 AI 规则；`tag-lexicon.json` 保留 aliases、groupLocked、reviewStatus 与 analysis。2026-09-10 按用户后续分析要求补强：新分析复用用户命名、别名、封面和自定义组，标准组即使已锁定仍须通过完整词义规则；本地/远程共用 `buildAnalyzedTagEntry`，不借旧包含匹配兜底。具体实体不因参数解析同时识别而被标签流程丢弃。自身证据不明或冲突、模型置信度不足的保留项进入待归纳，整理页不得重新提升不确定结果；模型置信度不等同于实测准确率。不得相信模型 normalizedLabel 合并不同实体，咖啡豆/咖啡、柔光箱/柔光、假山/假山石、红叶/黄叶必须区分。
6. 新增每个词或边界都要补正例和反例测试，例如芦苇/太阳/马匹/牵马绳的实体归类，以及太阳光、纯颜色和视觉属性的区分。旧库整理必须走「标签浏览→归纳整理」预览、逐项勾选和二次确认，禁止打开页面自动重写旧分组；原名称作别名，按提示词组去重计数。主进程使用白名单 IPC、库写队列与视图设置锁串行化，在两份 JSON 写入前保存 `tag-organization-undo.json`；支持最近一次整理撤销与重启恢复，预览过期或后续相关标签已改则拒绝覆盖。回归覆盖 `tagKnowledge.test.ts`、`tagOrganizationStore.test.ts`（选择范围、别名冲突、写盘失败回滚、撤销保护、导入导出元数据），以及 `scripts/check-tag-organization-ui.mjs`（宽窄窗口、自定义分组、依据、确认/返回、撤销与过期提示）。

### 统一回归边界
- 详情展示、library.json、view-settings.json、分类菜单计数、分类筛选、标签分组和重启恢复必须联合验证。`tagEntityGroups.ts` 使用完整实体名、受约束修饰和中心词，区分动物/配饰/服装结构、物体/材质、持物动作/所持物；手提包、手提篮、捧花优先作为成词物体，未知复合词不使用包含匹配兜底。用户要求仅复用「归纳整理」入口：标准分组与独立完整词义冲突时列入原有建议，已锁定项不默认勾选，用户可主动批量选择并二次确认；自定义路径保持原设置。多义词与依据不足项仍需复核。`tagEntityGroups.test.ts`、`tagOrganizationStore.test.ts`、浏览器宽窄窗口验证纠正/重开/撤销和后续识别；`check-tag-coverage.mjs` 只读审查所有组，在内存分别模拟默认选择与主动纠正，作品、封面、别名和未选择词条不得受损。
- 任何 AI 字段位置异常时宁可丢弃，也不得跨域兜底写入。2026-09-10 补充品牌/噪音边界：`tagQuality.ts` 区分相机品牌、型号、设备品牌、影像技术、来源水印、文案与碎词；新分析只认候选自身依据，用户已确认词库不能绕过新图的水印/碎词过滤，局部规则不改启动读库或普通导入。旧库可用同图器材/道路标签提出分组建议但不自动写盘。合法的 V2 空 tags 数组仅在标签任务按“无有效标签”处理，不重试、不回退凑词；畸形数组和分类任务继续保持错误校验。回归见 `tagQuality.test.ts`（SONY/α7C、HUAWEI/XMAGE水印、道/大、马/树/雾、原文与视觉证据、空结果单次请求）、`check-tag-organization-ui.mjs`（品牌分组、噪音提示、默认不勾选）。

## 文档维护规范

### 新增或遇到相似问题时的处理顺序
1. 先判断根因和解决方案属于 G01-G10 哪个主题，优先追加到已有主题的“共性根因”“统一方案”“统一回归边界”。
2. 只在历史追溯确有必要时新增一条短记录编号，并在对应主题的归并范围中追加编号；不得复制整套问题描述、根因、方案和验证。
3. 只有当新问题拥有不同的根因、不同的解决方案边界，且无法复用现有主题测试时，才新增 G11 等主题。
4. 目录中的简介和内容起始行必须在正文调整后同步更新；目录只写主题摘要，不重新展开正文。
5. 先搜索现有主题和规则，再修改代码；类似问题优先复用已有工具、日志事件和测试。

### 主题内追加格式
新增同类问题时只追加短条目，不复制完整记录：

    #### 追加：YYYY-MM-DD — [简短变化]
    - 归属主题：GXX
    - 历史编号：PXXX（如需追溯）
    - 新增证据：只写新的日志、数据或复现条件。
    - 统一方案变化：只写与现有方案相比新增的约束。
    - 回归测试：列出新增或更新的测试。

### 更新时机
- 修复完成且通过就近验证后更新对应主题。
- 发现同类问题时先合并，不得先创建新的长篇 P 记录。
- 规则、共享工具、数据 schema 或测试边界变化时同步更新主题。

### 关联文件
- 受影响的源码、测试、规则或打包脚本路径。
- 相关日志事件、错误码和正式包产物路径。
- 若主题涉及数据迁移、缩略图回退、图片复制或效果图排序，必须写明对应回归测试。
